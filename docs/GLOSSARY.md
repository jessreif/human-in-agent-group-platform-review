# Glossary

Terms used across the documentation, with the names they have in the code.

| Term | Meaning |
|---|---|
| Agent teammate | An automated team member. A session has two, shown to the participant by their initials, `JT` and `PM` (called seats in the code). |
| Assistant | An optional AI panel that answers questions about the participant's own case file. It was turned off in the pilots. |
| Profile | A JSON file in `content/profiles/` that specifies one study configuration: task, timing, agent teammate schedules, message banks, instruments, and conditions. |
| Manifest | A published profile. Publishing records its SHA-256 hash in `content/published/manifests.json`, and every session records the hash it ran under. |
| Arm, condition | One level of the experimental manipulation, declared under `manipulation.arm` in a profile. Arms in the code include `high`, `low`, and `mixed` (workload) and `eval` and `control` (peer evaluation). `nopress` marks sessions run with the time-pressure manipulation turned off; it is not an arm declared in any profile. |
| Check-in | A pause during the task in which each team member rates something, such as their workload. The ratings shown for the agent teammates are set by the profile. |
| Bank | A versioned file of pre-written messages under `content/scripts/`, used for scheduled messages and as fallbacks. |
| Conversational reply | A reply to something the participant typed that is not a request for task information. A profile's `social_generation` setting decides whether these come from the model (`model_with_validated_fallback`) or only from the banks (`deterministic_only`). |
| Check, fallback | Every model-generated reply passes rule-based checks (`validate_teammate_output`). A reply that fails is replaced by a pre-written fallback line. |
| Active time | The task clock. It pauses during check-ins, unlike wall-clock time. |
| Investigation Task | The task implemented so far: the team locates stolen crates across hideouts using intelligence records split among the members. The task world is generated by `build_world`. |
| Case file | The participant's own set of intelligence records. A thin case file has 20 records. |
| Overlap | Whether the participant's assigned crates are also assigned to the agent teammates (none, some, or full). |
| Batch, batch group | A recruitment round. Each condition has its own batch (`batch_id`) within a batch group (`batch_group_id`), such as `study.live.v14`. |
| Source fingerprint | A SHA-256 hash of the source code that identifies a build (`scripts/source_bundle.py`). |

## Internal codes

Code comments and the development records use these identifiers. They are kept so a reader can search for them across the documents.

| Code | Meaning | Where it is defined |
|---|---|---|
| `BA-*` | An audit finding and its fix | `agent/INVESTIGATORS_TEAM_EXPERIMENT_AI_AGENT_DECISIONS.md`, `IMPLEMENTATION_STATUS.md` |
| `AB-*` | A behavior of an agent teammate or the assistant observed during lab testing or a pilot | `agent/INVESTIGATORS_TEAM_EXPERIMENT_AI_AGENT_BEHAVIORS.md` |
| `AID-*`, `O-*`, `SQ-*` | A ruling on how the agent teammates or the assistant should behave | `agent/INVESTIGATORS_TEAM_EXPERIMENT_AI_AGENT_DECISIONS.md` |
| `D01` to `D14` | A research decision, such as payment policy or consent wording | `DECISIONS.md` |
| `WP*` | A work package in the implementation plan | `IMPLEMENTATION_PLAN.md` |
| `INV-*` | A task within a work package | `IMPLEMENTATION_PLAN.md`, `IMPLEMENTATION_STATUS.md` |
| `G1` to `G10` | A release gate: a set of checks a build had to pass before use with participants | `IMPLEMENTATION_PLAN.md` |
| `E1` to `E24` | A dated evidence package recorded during development | `IMPLEMENTATION_STATUS.md` |
| `UX_Feedback_vN` | A numbered round of usability feedback on the participant screens | `development-history.md` |
| `study.live.vN` | A recruitment round with participants. The pilots in `pilots/` are `study.live.v14` and `study.live.v15` | `../pilots/README.md` |
